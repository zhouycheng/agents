# Tailscale Docker Deploy

把项目安全地部署到 Linux Docker Compose 服务器。管理连接只用 Tailscale SSH；执行前检查项目的容器化状态、数据约定和服务器现状。

## 项目评估

1. 读取适用的 `AGENTS.md`、部署文档、当前 Git 状态、Dockerfile、Compose 文件、健康检查、环境变量和数据存储实现。保护已有改动，不输出 `.env`、密码、令牌或完整进程环境。
2. 已有可用 Dockerfile/Compose 时先复用，核对构建目标、服务名、端口、数据卷、健康检查及升级/恢复步骤；不要为形式完整而重写容器配置。
3. 没有容器配置时，先按实际运行时、构建依赖、外部服务、启动命令、持久数据和健康端点设计最小 Dockerfile 与 Compose。需要时补 `.dockerignore`、持久卷、健康检查和非 root 运行；密钥由受保护的运行时配置提供，不写入镜像或仓库。完成项目构建及适用检查后，再给部署方案或继续已获授权的部署。
4. 尊重项目对数据、审计记录和备份的规则。部署、重置凭据和缓存清理都不代表可以删历史；不得绕过应用的不可变约束。没有项目支持的安全清理机制时，保留数据并说明限制。

## 部署前检查

只有用户明确要求实际部署时才改变服务器；只要求方案时停在可执行方案。明确部署授权后完成以下检查，除非发现未解决的重大数据风险、目标歧义或超出授权的网络/安全变更，否则继续执行。

- 从本机 Tailscale 状态核对用户指定的服务器设备，再用 `tailscale ssh` 连接；核实远端主机名、Linux 系统和登录身份。连接失败时不改用普通 SSH。
- 核实 Docker Engine、Compose、当前项目和服务健康状态；盘点 CPU、内存、磁盘余量、端口占用、现有容器/服务、挂载和命名卷。只读取完成判断所需的元数据，不打印含密钥的环境变量。
- 对照项目约定确认持久数据位置、备份范围、备份可用性和恢复方式。需要备份时先完成并核对备份；项目要求隔离恢复验证时，先在独立数据卷验证。无法满足数据保护要求就停止有数据风险的更新，并说明缺口。
- 确认 Compose 项目和本次操作边界，只影响目标服务及其确有必要更新的依赖；不重启或改动无关服务。

## 执行和回滚

1. 记录当前 Compose 配置版本、目标容器使用的镜像及健康状态。保留旧镜像和项目要求的协调备份，准备恢复原配置与镜像的回滚步骤。
2. 按项目的构建与配置方式生成或拉取新镜像，然后只更新目标 Compose 服务。不要把凭据放入命令参数、提交、镜像层或日志。
3. 检查容器状态/健康检查、应用健康端点及必要的应用级只读行为；检查有限范围的脱敏日志。健康检查成功只证明该端点覆盖的能力。
4. 若新版本不健康，先收集诊断并恢复旧镜像和配置，持久数据按项目恢复流程处理。不要未经验证就覆盖当前数据；遇到不可逆迁移或需要丢弃数据时停止并说明，等待用户决定。
5. 不运行 `docker compose down -v`、卷删除、数据库历史删除或全局 prune；不自动清理旧镜像、缓存、数据卷或历史记录。

## 访问入口

- 用户需要公网访问时默认采用 Tailscale Funnel；它会把服务开放给互联网任何访问者。当前文档要求 MagicDNS、HTTPS 证书和 tailnet Funnel 策略，域名限 tailnet 的 `.ts.net`，监听端口限 `443`、`8443`、`10000`；部署时重新核对这些会随版本变化的要求。先看 `tailscale funnel --help` 和 [Funnel 官方文档](https://tailscale.com/docs/features/tailscale-funnel)，不照抄旧版命令。HTTPS 证书的设备名和 tailnet DNS 名称会写入公开证书透明度日志；在启用许可页出现时说明这一点，尚未获用户确认则停在该确认点。参阅 [HTTPS 证书说明](https://tailscale.com/docs/how-to/set-up-https-certificates)。
- 仅供 tailnet 内访问时使用 Tailscale Serve，并核对当前命令、HTTPS 和访问控制；其访问范围不同于 Funnel。参阅 [Serve 官方文档](https://tailscale.com/docs/features/tailscale-serve)。
- Funnel 不可用或用户明确要求自有域名时，检查现有反向代理、DNS 目标、服务器公网可达性和防火墙范围；复用已有代理并让应用只在本机或私有容器网络监听。公开 DNS/反向代理/HTTPS 设置不得暴露应用原始端口。没有可用的 DNS 管理能力时，根据已核实的公网目标列出所需 DNS 记录并停在可执行方案，不猜测 IP、不代用户修改 DNS。不得修改用户 Mac 的 DNS 或代理设置。

## 验收与汇报

- 回读 Compose 服务状态、健康检查和应用健康端点；确认持久卷仍挂载、无关服务仍正常。
- Funnel 公网验收必须从不在该 tailnet 的网络请求实际 URL；tailnet 内请求、Tailscale 状态或配置成功都不能单独证明公网可达。无法从外网测试时明确标为未验证，不声称“所有人都可访问”。Serve 则从获准的 tailnet 设备验证。
- 汇报服务器身份、目标服务、镜像版本、健康端点、数据备份与卷、访问入口、实际测试网络和未完成项；区分容器健康、应用健康和外网可达性。
